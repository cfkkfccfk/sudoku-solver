Part3 · 异步调度（Async Scheduling）

CPU 调度与设备 forward 重叠　｜　num_output_placeholders 占位符记账　｜　叠加 MTP 后的两处回退

本篇定位

前置：Part1「一步数据流」（step() 的调用序）与「execute_model / sample_tokens 两阶段」。Part1 那句"异步调度时与下一步调度重叠"就是本篇展开的东西。

一句话：异步调度让引擎侧的 CPU 工作（调度、状态回写、detokenize 准备）与设备侧的 forward 重叠，办法是"先按乐观假设调度下一步，不等这一步的采样结果落回 CPU"。代价是引入一套占位符记账，以及若干特性不兼容。

与 Part2 的分工：Part2 统一按同步调度讲（schedule → execute → update_from_output 首尾相接）；异步调度的全部内容——欠条记账、稳态时间线、MTP 的两处回退——集中在本篇。Part2 只在三处留了指针，不做展开。

代码口径：vLLM 0.14.0 vllm/、omni-npu omni_npu/。默认按单实例讲，PD 分离与多 DP 的差异指向 Part4。

动机

1　要解决的问题：同步调度的两段空等

同步调度下，一步之内 host 与设备严格轮替：host 调度时设备闲着，设备计算时 host 停在那里等结果。两段空等都是纯损失。

sched N 一结束设备就接上 Forward N；host 随即进入空等，直到右侧那个对齐点——整步唯一必然阻塞 host 的地方。
关键在于：host 空等期间设备一直在算。所以损失不是那几百字节的拷贝，而是host 陪着一起停——它本可以拿这段时间去调度下一步。

那它为什么非等不可？schedule() 自己只做一次减法（目标 − 游标），压根不读 token 的值。但同步实现下，「目标」增长的唯一通路要经过 update_from_output——而那必须先拿到值。于是 schedule 被这条通路间接卡住了：

卡点不是游标——游标早在 schedule(N) 末尾就推过了（Part2·1.3）。卡的是「目标」：decode 请求的 num_tokens 只能靠 update_from_output 追加 token 才增长。目标不长，目标 − 游标 = 0，下一步一个 token 都调度不出来。

思路：既然 schedule() 本来就只要个数，那就别再让「目标增长」绕道 update_from_output——先按乐观假设把目标顶上去、把下一步调度出去，「到底是哪几个」推后处理。
落到实现上，正是拆开上面那条依赖的两半：把「等」从主线程挪走（2.3）＋ 在目标侧先记一笔欠条（2.2）。缺一不可——只挪 D2H，调度仍要等目标增长；只记欠条，输出仍会堵住主线程。
总览

2　三层配合：引擎、调度器、Worker

异步调度不是单点改动，而是引擎、调度器、Worker 三层各改一件事，缺一层就不成立。三处改动都落在 Part1 那张「一步数据流」上——把它摊在这里，后面 2.1 / 2.2 / 2.3 不必再翻回去：

同步路径的一步（摘自 Part1·2.1），与异步调度的三处改动落点

① API Server：tokenize → EngineCoreRequest　—— ↓ ZMQ 第一跳 ↓ ——
② EngineCore（run_busy_loop 每步循环）· step()2.1　整个换成 step_with_batch_queue()
schedule() → SchedulerOutput（跑谁 / 各几 token / KV 块）2.2　调度完就记一笔欠条
↓ Executor 广播（共享内存 MessageQueue）　　↑ Worker 回传2.1　回传不当场收，记进 batch_queue
③ Worker：打平输入 → forward → 采样 → ModelRunnerOutput2.3　token 的值全程留在设备上
update_from_output → 推进状态 / 释放 KV / 出 EngineCoreOutputs2.1　挪到下一次调用才做
—— ↓ ZMQ 回程 ↓ ——　① API Server：detokenize → RequestOutput

三层是一条「缺一不可」的因果链：2.1 让引擎可以提前调度下一步 → 但调度得知道各请求现在有多少 token → 2.2 用欠条顶上 → 但 forward 要真实的 token id 才能算 → 2.3 让 token 的值留在设备上。
主线一句话：CPU 只管「有几个 token」，不管「是哪几个」；值在设备上流转，搬回 CPU 只为 detokenize 与判停，可以慢一步。

引擎侧

2.1　引擎侧：让两个 step 同时在跑

开关一开，一条链就串起来了：Executor.max_concurrent_batches 从「PP 级数」改成返回 2 → batch_queue_size = 2 → batch_queue 非空 → 主循环换函数，step() 变成 step_with_batch_queue()。

换函数换掉的是一件事：EngineCore 调完 sample_tokens（Executor 上的 RPC 存根，只负责把方法名广播出去；真正的采样在 worker 进程里跑）后不再原地等它的返回值，而是把「这一步的输出待取」记进 batch_queue（代码里就是一个 Future[ModelRunnerOutput]），留到下一轮再收。回到上面那张图看——batch_queue 就是缓存「Worker 回传」那条箭头的地方：同步路径下「广播 ↓」与「回传 ↑」在同一次 step() 调用内首尾相接，回传一到就被 update_from_output 吃掉，不需要任何容器；异步下这条箭头被挂起，update_from_output 挪到下一次调用才做。于是主循环的节奏变成：

「对账」= 三个动作：从 batch_queue pop 出最老那一批 → 阻塞等它的输出 → update_from_output 回写（第 4 节图里 EngineCore 泳道的「阻塞等 Out N」+「↩ upd N」两格）。
两种「输出」别混：EngineCore 等的是 worker 回传的 ModelRunnerOutput（第 4 节的 Out N，与 MTP N 并行落地）；而这里送出的是 upd N 产出的 EngineCoreOutputs——前者是后者的输入。
「空手返回」= 这次不做对账，只把队列填上——step_with_batch_queue() 的返回值第一项直接是 None（没有输出要送 API Server），主循环立刻再调一次。它只发生在注满阶段：稳态下派发完队列就满了，每次调用都必须对账、也就都有输出——所以第 N 步的输出是在第 N+1 次调用里送出的（wall-clock 时刻与同步路径一致，只是记在了另一次调用名下）。
它还带一个条件：队尾那批已经算完时 CPU 不抢跑，直接转去对账——避免设备已经空出来了、CPU 还在往前排队。

为什么恰好是 2，而不是更多：两次 schedule() 之间隔着一次"等输出 + 对账"，于是任何时刻最多只有 1 个 step 未对账。乐观只乐观一步——这就是后面第 3 节的回退永远只需覆盖一个 num_rejected、不会累积成"回退 n 步"状态机的根本原因。batch_queue_size = 2 把这个数直接钉死了。
调度器侧

2.2　调度器侧：AsyncScheduler 的"欠条"记账

2.1 让引擎"可以"提前调度下一步，但没解决"凭什么调度"——这是异步调度的记账基础，也是它引入的唯一一个新概念。

核心矛盾：调度第 N+1 步需要"各请求有多少 token"，而第 N 步的 token 还在设备上

要什么调度第 N+1 步 → 需要各请求现在有多少 token
（算 num_new_tokens、分 KV、扣预算）
✗
有什么第 N 步的 token 还没落回 CPU
（值还在设备上，见2.3）
↓ 关键观察
调度只需要"几个"，不需要"是哪几个"→ 那就先乐观记一笔欠条，把个数补上，值留着以后再说

落地就是换一个调度器子类 AsyncScheduler（按 async_scheduling 选类，全文仅 67 行）。它把账记在 schedule() 的最后一步 _update_after_schedule 上：先推游标——对本步所有被调度请求统一 num_computed_tokens += num_scheduled_token；再对其中会产出新 token 的那些多记一笔欠条。两笔都只改 Scheduler 内存里的 Request，不进已经定型的 SchedulerOutput。

# 调度后：本步一定会产出 1 + num_spec_tokens 个 token —— 先记上
if request.num_computed_tokens == (request.num_tokens
                                   + request.num_output_placeholders
                                   + cur_num_spec_tokens):
    request.num_output_placeholders += 1 + cur_num_spec_tokens
    request.spec_token_ids = [-1] * self.num_spec_tokens   # 占位，真值由 worker 侧填
# 真 token 回来时冲销
request.num_output_placeholders -= len(new_token_ids)
assert request.num_output_placeholders >= 0

所以 num_output_placeholders 的语义是："已经按它调度过、但还不知道具体是什么"的 token 数。同步调度下它恒为 0——这正是 Part2 那句括号说明的由来。

一个请求的 token 账：欠条把"已知段"与"已调度但值未知段"分开

两处必须为"值未知"让路

欠条段没有内容，于是凡是依赖 token 内容的机制都得退到已知段为止：

　让路做法为什么
① prefix cache 只缓存到 num_computed_tokens − num_output_placeholders block hash 要按 token 内容算；欠条段还没有内容，进不了缓存 → 命中率会略降
② 判停 要看 token 值的停止条件（EOS / stop_token_ids / stop 串）必然多跑一步，那一步的产出作废 schedule(N+1) 时第 N 步的值还没回来，判不出停没停，只能照排照跑；等 upd(N) 发现停了，请求已被释放，第 N+1 步的产出就没人认领了。
max_tokens 是例外——它只看个数，所以 RUNNING 扫描一进门就能提前跳过，不浪费这一步。
把两条合起来看：欠条只在"计数"这个维度上可信——凡是要读 token 内容的地方（缓存、判停），都必须回退到已知段的边界上。这是 num_output_placeholders 带来的全部复杂度所在。
其中「多跑一步」是异步调度最容易被忽略的一笔固定开销，而且与 MTP 无关——换来的是每步都省下的 CPU 气泡。
Worker 侧

2.3　Worker 侧：token 值全程留在设备上

调度器可以只认个数，但 forward 必须拿到真实的 token id。Worker 侧两件事把这个缺口补上，且都不占用主线程。

a采样结果延迟搬回 CPU，等待交给独立线程

采样照旧在设备上完成，但 sample_tokens 返回的不再是现成的 ModelRunnerOutput：它只在独立 copy stream 上发起一次非阻塞 D2H、记一个 event，不 synchronize。主线程把这个半成品甩进队列就走，「等 event 落地、填好 token、回包」全部交给一条专门的输出线程。

这就是异步调度真正的关窍：token 的值全程留在设备上流转，CPU 只管"有几个 token"，不管"是哪几个"。搬回 CPU 只为了 detokenize 和判停，所以可以慢一步。2.2 的欠条之所以够用，全靠这一节兜住了正确性。

开 MTP 时每个 decode 请求占 1+k 个连续空洞——1 个 bonus token（上一步采样的）＋ k 个草稿，值同样全在设备上，同样在设备上 scatter 进 input_ids，不走 CPU。

MTP 叠加

3　叠加 MTP：被拒时的回退落在哪

异步调度按"draft token 全部被接受"乐观调度下一步，而 MTP 的草稿可能被拒。要回答的问题是：这个回退具体在哪执行？是不是 schedule(N+1) 之后要额外插一个回退步骤？

结论：没有额外步骤。回退寄生在两处本来就要跑的代码里，而且是两套账各自减一次——Worker 一份、Scheduler 一份，互不依赖。整个"回退"只落在一个标量 num_computed_tokens 上：没有 rollback 状态机、不重调度、不丢弃已派发的 batch。

update_from_output(N) 里那句"游标回退"确实排在 schedule(N+1) 之后，所以它管不到第 N+1 步。管得到的是 Worker 那一次。

1回退一：Worker 侧，在第 N+1 步 forward 的输入准备里（保正确性的那次）

execute_model(N+1) 的第一件事是 _update_states(scheduler_output_{N+1})，它在 _prepare_inputs 之前就把游标改对：

调度器发来的 num_computed_tokens 是乐观值（C + 1 + k）。Worker 拿它去建 positions / seq_lens / slot_mapping / attn_metadata 之前先扣掉被拒数 → forward N+1 算的是正确位置。

prev_num_draft_len 是上一步实际调度给它的草稿数；等于 0 时整段跳过——第一步与 prefill 步都不需要回退。

2回退二：Scheduler 侧，在 update_from_output(N) 里（只是账本对齐）
num_accepted = len(generated_token_ids) - 1
num_rejected = num_draft_tokens - num_accepted
request.num_computed_tokens     -= num_rejected   # 游标
request.num_output_placeholders -= num_rejected   # 欠条（2.2）

它排在 schedule(N+1) 之后，对第 N+1 步已做出的决策毫无影响，只影响 schedule(N+2) 起的 KV 分配、判停、prefix cache 上界。

注意欠条那一行：2.2 的 -= len(new_token_ids) 冲销的是"真回来的 token"，这里的 -= num_rejected 冲销的是"预支了但没兑现的"。两者相加，才把 += 1 + cur_num_spec_tokens 那笔预支清干净。

3.2　为什么 schedule(N+1) 不用重做

这是整套设计最省事的地方：拒绝几个，不改变"下一步算几个 token"，只改变"从哪个位置开始算"。第 N+1 步永远是 1 个 bonus token + k 个新草稿，与接受数无关。

schedule(N+1) 乐观决定的东西被拒后要不要改为什么
num_scheduled_tokens = 1 + k不用验证 batch 的形状与接受数无关
positions / seq_lens / slot_mapping 的起点要改Worker 在 _update_states 里扣 num_rejected（回退一）
KV slot 分配不用多分的槽位没被写入；游标回退后下一步原地覆盖复用
token_budget / max_num_seqs 记账不用偏乐观而已，无正确性影响
prefix cache不用本来就只缓存到 num_computed_tokens − num_output_placeholders（2.2 ①）
一句话记忆：num_scheduled_tokens 是对的，只有起点错了；把起点减掉 num_rejected 就全对了——所以回退是一次标量减法，不是一个步骤。

三条读图要点：

  • sched N+1 与 Forward N 同列——调度不等设备：门槛只是 batch_queue 未满（size=2），派发本身是一次共享内存投递、微秒级。代价是它不知道第 N 步接受了几个，只能按"draft 全被接受"记欠条（2.2）。
  • ↩ Input N+1 与 MTP N 同列——保正确性的那次回退：count N 走独立拷贝流、早于 MTP 落地，Worker 得以在建输入张量前把游标减回真实值，Forward N+1 才算在对的位置上。这是异步链路上唯一残留的硬依赖。
  • ↩ upd N 只对账本：同一个 num_rejected 在 CPU 侧再减一次（游标 + 欠条），最早影响 sched N+2，管不到已派发的第 N+1 步。不会重复扣——两处减的是各自的副本（Worker 减 req_state、Scheduler 减 request），各减一次、永远对得上。
三条设备流的分工，正好对应"CPU 只管有几个 token、不管是哪几个"这条主线：主计算流跑真活；接受数拷贝流只回传一个小整数、喂给下一步的输入准备（唯一硬依赖，压到最小）；异步输出流回传完整 token id，慢一步无所谓。
副作用

5　一处连带副作用：DP 同步被迫改走 CPU

5.1　为什么必须有这一步

DP（数据并行）本意是各 rank 独立跑不同请求、互不通信。但以下三处会打穿 DP 边界，逼各 rank 必须步调一致：

  • MoE 专家并行（EP）的 all-to-all：开 EP 后 MoE 每层要把 token 按路由 all-to-all 分发到各 rank 的专家再收回，要求各 rank 进 all-to-all 的 token 数一致。
  • lm_head 的 DP 切分：vocab 很大，按 DP 维切 vocab 后算 logits 要 allgather + all-to-all——同样跨 DP。
  • 整步 lockstep：集合通信要求所有参与方到齐，只要有一个 rank 缺席，其余 rank 就会永久挂起。

而各 rank 各自独立调度，每步的 num_tokens 天然不同。于是每次 forward 之前先做一趟小 all_reduce 换取全局视野，按两条规则得出统一决策：num_tokens 取全局 max（谁多按谁来，短的 pad 上去）、cudagraph_mode 取全局 min（有一个 rank 走不了图，全体降级 eager）。

5.2　异步调度把它撤到了 CPU：因为一个假依赖

开异步调度会把这趟 all_reduce 从设备通信域自动改走 CPU——仅当用户没有显式指定时才自动翻：

# config/vllm.py —— 用户没显式指定时，跟着 async_scheduling 自动翻
if disable_nccl_for_dp_synchronization is None:
    disable_nccl_for_dp_synchronization = async_scheduling

# dp_utils.py::_get_device_and_group —— 翻成 True 后改走 gloo
# 注释原文：把这个张量从 GPU 搬到 CPU 会引入一个 GPU sync point，
#          可能损害开了异步调度的 vllm 的性能
if disable_nccl_for_dp_synchronization:
    device, group = "cpu", get_dp_group().cpu_group

为什么结果非得读回 host：max / min 本身是在设备上算的，逼出同步的是随后的 .item()——而它非做不可，因为这三个结果都要当 Python 的控制流条件用：pad 到多少、选哪一张捕获图、走图还是 eager。设备张量驱动不了 Python 的 if。

而这次回读的代价和前面同一个形状——在流上的排队顺序：那个 D2H 同样挂在主计算流上，那里正排着上一步的工作：

D2H 前面不再排着 forward N，只等 all_reduce 本身 → 同时拿到设备互联的低延迟与不序列化。它完全绕开 _get_device_and_group()，也就绕开了 disable_nccl_for_dp_synchronization 这个变量——是一条并列的独立实现，不是在 gloo 那条路上再改一层。

前两条只是「让侧流存在」，第三条才让侧流在 forward 满载时真的能向前推进。净收益方向：收益是每步、每次 forward 的——320 字节纯延迟敏感小包，HCCS/RDMA 远低于 16-rank TCP gloo，开 MTP 还 ×2；抖动从「16 台机器的 Linux 调度器」换成设备控制核，TPOT p99 收紧；代价却是静态一次性的——每 rank 20MB HCCL buffer 从 KV cache 预算里扣。静态换动态，方向有利。
