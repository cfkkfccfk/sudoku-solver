vLLM 框架

1　三进程与部署拓扑

为什么要拆进程：GPU/NPU forward 只是推理系统的一环。一条请求从进入引擎到吐出 token，中间还要经过调度、显存管理、跨进程通信、KV 传输，这些环节才真正决定系统的吞吐（Throughput）与时延（TTFT / ITL）。把「HTTP/tokenize」「调度」「forward」拆到不同进程，是为了让 CPU 密集的请求处理、Python 单线程的调度、设备密集的计算能并行流水，互不阻塞。

1.2　进程拓扑的两种形态：混布 vs PD 分离

前面讲的三进程，是一个实例（instance）内部的样子。真实部署有两种拓扑：

混布（co-located，默认）
prefill 和 decode 跑在同一个实例里——同一套三进程、同一个 Scheduler、同一批 Worker、同一份 KV。两类请求在同一个 batch 里混算（chunked prefill + continuous batching）。前面 1.1 讲的就是这种。
PD 分离（disaggregated）

3.1　两类入口：在线 vs 离线

关键认知：两类入口共用同一套第 1 节的引擎内核（EngineCore + Scheduler + Worker）、也共用 3.3.2 的同一套初始化流程，区别只在最前面那层"谁把请求喂进来"、以及进程与分布式组是谁拉起的。

3.1.1　在线：常驻 API Server
vllm serve <model> 起一个常驻服务，就是第 1 节那张图的原样：
· 进程① = AsyncLLM + OpenAI HTTP 接口
· 经 ZMQ（第一跳）连到进程② EngineCore，后者驱动进程③ Worker
· 请求经 HTTP 持续、异步到达（"活水"），引擎 busy loop 常驻空转等活
第 1–2 节描述的默认就是这种形态；3.2 起的实机日志走的也是这一路。
3.1.2　离线：一个脚本喂一批 prompt
LLM(...) + llm.generate([prompts])。没有 HTTP 服务：
· 你的 Python 脚本本身就是"前端"
· 把一批已知的 prompt 交给引擎
· 引擎跑到全部结束、返回结果，脚本退出
一个易误解点：离线不等于"单进程同步跑"。默认 VLLM_ENABLE_V1_MULTIPROCESSING=1，LLM 背后的 EngineCore 仍跑在独立子进程里（含第 1 节的 busy loop），脚本通过 ZMQ 把 prompt 逐条发过去。设 =0 才切成进程内同步（InprocClient），全部 prompt 先同步入队再 step。
由此决定"请求顺序可控到什么程度"：三层分开看
层次离线默认（=1）离线 =0为什么
提交顺序可控，就是你列表的顺序可控generate() 先按列表逐条 add_request 全部提交完，才调 _run_engine() 开始取结果
哪几条落在同一个 batch不可控可控=1 时对端 busy loop 与你的发送循环并发，没有"等我发完"的同步点，第 1 条到了就可能开跑；=0 时 add_request 只是同进程入队、没有 busy loop，全部入队后才 step
实际执行顺序只有 FIFO 倾向同左进了 WAITING 队列后还受 token 预算、KV 够不够、抢占、priority 调度影响Part2

在线连第一层都不保证：并发请求的到达顺序本身就不确定。

离线又分两种形态，取决于要不要数据并行（DP）
3.1.3　纯单进程离线（DP=1，vLLM 全托管）
一个脚本进程跑 LLM(...)、data_parallel_size=1。TP 的多卡 worker 由 vLLM 内部 spawn，你不管进程拓扑。
代码硬性限制：单进程里 data_parallel_size>1 会直接抛错（not supported for single-process usage and may hang）——想开 DP 就得走右边这条。
3.1.4　手动 mp DP（DP>1，你自己起 N 个 rank 进程）
要开数据并行（例如常用的 DP8/EP8 组合），得自己用 multiprocessing.Process 起 N 个进程、每进程绑一个 DP rank：
· 每个 rank 先手设分布式 env（RANK / WORLD_SIZE / MASTER_ADDR / VLLM_DP_*），各自建 LLM(..., distributed_executor_backend="external_launcher")
· external_launcher = vLLM 不替你建进程拓扑，只加入你已建好的 HCCL 世界组
· N 个 rank 各处理不同的一批请求（数据并行），但因为 MoE 开了 EP，每层还要跨 rank all-to-all，步调必须一致 Part3 多 DP padding

3.3.3阶段 3 · init_device()：绑卡、建通信域

三件事：绑定本 rank 的设备 → 建出各级通信域（init_process_group 先立 world group，再按 TP → DCP → PCP → PP → DP → EP 的顺序逐级切分 rank，每级一个 GroupCoordinator）→ 构造 ModelRunner。各域的成员由 rank 布局顺序决定，越靠内层的维度 rank 越连号，所以它同时决定了哪些通信落在机内、哪些要跨机。

一个"通信域" = 一个 GroupCoordinator = 两个 torch 进程组：一个 device group（NPU 上是 hccl）+ 一个 cpu group（gloo，用于不走设备的协调，如多 DP padding 的同步）。域的实际数量要乘 2。

建完即定死：整个服务生命周期内进程拓扑与通信域都不再变——这既是 3.1.4 说的"进程拓扑不能中途改"的物理原因，也让这一步成为启动期最常见的卡死点（rank 没齐、端口被占、网卡不通都停在这里）。

但主力域建完不等于全部域都建完——还有些域是懒建到首个请求的；这一点连同 NPU 在建组时注入的调优项，都见 4.3.2。

3.3.4阶段 4 · load_model()：载权重与权重改造

两件事：把本卡那份权重分片按名字灌进已建好的层（开投机解码时再载一次草稿模型）；随后 process_weights_after_loading() 把权重就地改造成推理要用的形态。

第二件事是重点：磁盘上的权重形态和算子想吃的形态往往不一样——要转置、拼接、换 layout、把 scale 展平、做 requantize。这些只需做一次的事全部提到启动期，forward 里就不必重复；它同时决定了权重的最终显存占用，阶段 5 才测得准。框架只负责"遍历所有 module + 调约定的钩子"，具体改什么由每层自己决定。

一点容易读错：Model loading took xxx GiB 是本卡分片（整模型按 TP/EP 切分后落到这张卡的那一份）、且已含草稿模型，不是整模型大小；草稿模型通常共享 embedding 和 lm_head，几乎不额外占显存。

一句话：omni-npu 用两条腿接管 vLLM——① 平台 hook「换类」（worker/图/通信/attention backend 整类替换成 NPU 版）；② monkey-patch「改方法」（对只需改个别方法的地方，就地替换 vLLM 类/模块上的函数）。两者都不 fork vLLM 源码。

本节是"某一个具体插件"的实现：昇腾生态里适配 vLLM 的插件不止一家（如 vllm-ascend），它们接管的位点是同一批——entry point、平台 hook 换的类、patch 的方法、以及八阶段里的插入点。换插件分析时，第 1–3 节可直接复用，只需照本节的顺序把这几处重新填一遍。

4.1　接管机制：两个 entry point、三种手法

vLLM 启动时用 importlib.metadata.entry_points() 扫描已安装包注册的入口点。omni-npu 往两个入口点组里注册了三个入口：

[project.entry-points."vllm.platform_plugins"]
omni-npu = "omni_npu.vllm_plugin:plugin"                     # ① 平台插件

[project.entry-points."vllm.general_plugins"]
omni_npu_patches  = "omni_npu.vllm_patches:apply_patches"    # ② monkey-patch
omni_custom_models = "omni_npu.v1.models:register_models"    # ③ 模型注册
  • vllm.platform_plugins：vLLM 探测硬件平台时调用，决定"这是什么设备"。
  • vllm.general_plugins：vLLM 初始化时统一 load，做通用扩展。
三个入口 = 三种手法
① 换类　plugin() → NPUPlatform
平台 hook 把 vLLM 的默认实现整类换成 NPU 版：worker 类（最关键）、图执行器 → ACLGraphWrapper、通信 → NPUCommunicator（HCCL）、attention backend → NPUMLA / NPUDSA、图编译 pass；顺带注册自定义算子层与 KV connector
② 改方法　apply_patches()
monkey-patch：对只需改个别方法的地方，就地替换 vLLM 类或模块上的函数。目标可以是类（如 Scheduler.update_from_output）也可以是模块（如 dp_utils 里的 DP 同步函数）。补丁分两批：公共补丁全导入，模型专属补丁按 model_type 选目录导入
③ 注册模型　register_models()
把 omni-npu 中的 Pangu V2 模型层 提供的模型类登记进 vLLM 的模型注册表，使 config.json 里的 architectures 能解析到这些实现

前两种是接管 vLLM 行为的"两条腿"，第三种只是往 vLLM 里加一个模型、不改框架行为。三者都不 fork vLLM 源码。

「换类」里最关键的一步在 check_and_update_config——它把 worker 类换成 NPU 的：

1　调度工作原理：continuous batching 的调度端

本节位置：对应 1 数据流图里 EngineCore step() 的第一步 schedule() 与最后一步 update_from_output——"决定这步跑谁、各几 token" + "跑完回写状态、腾 KV"。中间的 forward 是 Part1·2.2。

核心结论：vLLM V1 调度器没有"prefill 阶段"和"decode 阶段"之分。每个请求只是一个游标——num_computed_tokens（已算到第几个）在追 num_tokens_with_spec（一共要算到第几个）。每步 schedule() 就是给各请求分配 token、让游标前移。prefill / decode / chunked prefill / prefix cache / 投机解码全统一成这一个动作——这也是 continuous batching 的地基。

调度器主体在 vLLM 框架（scheduler.py）；NPU 侧没有任何平台适配——调度器跑在 EngineCore 进程里、通篇不碰设备 API → 本节是纯 vLLM 逻辑。

麻烦在于"流动的 batch"里每条请求这步要算的 token 数都不一样（decode 1 个 / 新 prefill 一大截 / chunked 一截）。若按 [batch, seq] 二维张量，就得 padding 到最长的那条，短的全是废计算。vLLM 的解法是根本不用 batch 维：_prepare_inputs 把所有请求这步要算的 token 首尾相接拼成一维 input_ids，长度 = total_num_scheduled_tokens，不做 padding（主体在基类 gpu_model_runner.py，NPU 仅薄封装）。

模型端的输入契约：顶层 forward 收 [num_tokens, hidden]

打平后的一维 input_ids 直接进模型顶层 forward——vLLM V1 里所有模型签名统一，收 input_ids / positions，没有 batch 维：

def forward(self, input_ids, positions, intermediate_tensors=None, inputs_embeds=None):
    hidden_states = self.embed_tokens(input_ids)      # [num_tokens] → [num_tokens, hidden]
    for layer in self.layers:
        hidden_states = layer(positions, hidden_states, ...)
    return hidden_states                              # 全程第 0 维 = 本步 token 总数

模型内部所有张量第 0 维就是"这步 token 总数"，全程没有 [batch, seq] 二维结构。decode 的 1 个 token、prefill 的一大截 token 首尾相接、同一次 forward 一起算完。per-token 的层（embed / MLP / norm / MoE）逐 token 独立、不关心请求边界，拿到 [任意 token 数, hidden] 就能算；唯独 attention 有 token 间依赖，需要额外信息把请求认出来（2.2）。

这是所有被搬进 continuous batching 框架的模型都要做的通用改写（相对原生 HF 的 [batch, seq] + padding），Pangu 模型只是照契约写。

2.2　Attention 怎么在打平流里重新区分请求：四种实现递进对照

打平之后，[num_tokens, hidden] 里从形状上根本看不出谁是 prefill、谁是 decode。per-token 的层不在乎；唯独 attention 有 token 间依赖（同一请求内因果可见、要查该请求历史 KV），必须知道"哪些 token 属于同一请求、是 prefill 还是 decode"。

区分信息全在 attn_metadata 里，不在张量形状里。 _build_attention_metadata 把它们打包成与后端无关的 CommonAttentionMetadata，经 set_forward_context 挂到 forward context 供 attention 取用。它有两类字段：计数标量与索引/长度张量：

两条恒等式（记忆锚）：把计数按相位一分为二——条数 num_reqs = num_decodes + num_prefills；token 数 num_actual_tokens = num_decode_tokens + num_prefill_tokens。其中相位计数 num_decodes / num_prefills / num_decode_tokens 不在通用 metadata 里——只有"要切相位"的后端才现算它们（下文"P/D 分离"一节的 split_decodes_and_prefills）；FlashAttention 一把吃混排，压根不需要。

到此为止都是框架通用契约。 但"拿到 metadata 之后具体怎么算"——一个 kernel 全吃下，还是先按相位切开各算——不同后端差异巨大。下面从最朴素到昇腾 / Pangu 递进对照四种实现。

一基于 FlashAttention 的朴素实现（GPU 默认）

最朴素：一个 varlen kernel 直接吃下整条混排流，不重排、不切相位。 vLLM 的 GPU 默认后端 FlashAttention（flash_attn.py）：不做任何 reorder（不设 reorder_batch_threshold）→ 请求保持调度器原顺序、decode/prefill 可交错；forward 里一把 flash_attn_varlen_func，cu_seqlens_q = query_start_loc、KV 靠 block_table 分页、causal=True。一个 decode 请求 = query 长度 1 的序列、prefill = 长度 N 的序列，对 varlen kernel 只是"一批长度各异的序列"，一次 launch 全算完。

这就是为什么 2.1 的"打平 + metadata"在 GPU 上开箱即用：FlashAttention varlen kernel 把"识别每条请求边界、逐序列施因果 mask"吃进了内核内部，框架层无需相位切分。

二基于 P/D attention 分离的实现（FlashInfer / MLA）

不是所有 GPU 后端都能一把吃下。FlashInfer 和 MLA（DeepSeek 系）在 GPU 上就要把 decode / prefill 切开各算：MLA（声明 reorder_batch_threshold=1）decode 走"矩阵吸收"、prefill 走普通算法；FlashInfer 用分开的 decode / prefill wrapper。这件事分两步做，都是 vLLM 上游 attention/backends/utils.py 里的通用函数：

① 入 batch 时重排——reorder_batch_to_split_decodes_and_prefills 按 decode → extend → prefill 重排、让同类挤在一起，由 reorder_batch_threshold 驱动、每步入口跑一次、直接交换持久 InputBatch 槽位：

decode_threshold 就是这个后端声明值，语义是"query 长度 ≤ 它就算 decode、要被挪到队首"：FlashAttention 声明 None（= 不重排），MLA / FlashInfer / 通用昇腾后端声明 1；后端若有能吃 "1+N query" 的 decode kernel（supports_spec_as_decode），构造时会抬成 1 + num_speculative_tokens，让投机验证步仍算 decode。① 的重排与 ② 的切分共用同一个值，所以两者边界必然一致。
is_prefill = num_computed_tokens_np == 0                                    # 没历史 → 纯 prefill
is_decode  = (num_scheduled_tokens_np <= decode_threshold) & ~is_prefill    # 只算 ≤阈值 个 → decode
is_extend  = (num_scheduled_tokens_np >  decode_threshold) & ~is_prefill    # 有历史但算多个 → extend
# 目标顺序 decode → extend → prefill，凡不在位的用 input_batch.swap_states(src, dst) 原地交换

② forward 前算分界——split_decodes_and_prefills 在已重排的流里定边界。判定规则：query_len ≤ decode_threshold(=1) 即算 decode；因已 decode-first 重排，只需找第一个超阈值请求当 prefill 起点：

query_lens = query_start_loc[1:] - query_start_loc[:-1]              # 每请求这步的 query 长度
if max_query_len <= decode_threshold:   return (num_reqs, 0, num_tokens, 0)   # 快路径：全 decode
if query_lens[0]  > decode_threshold:   return (0, num_reqs, 0, num_tokens)   # 快路径：全 prefill
first_prefill      = (query_lens > decode_threshold).int().argmax()  # 混排：第一个超阈值请求下标
num_decodes        = first_prefill
num_prefills       = num_reqs - num_decodes
num_decode_tokens  = query_start_loc[first_prefill]                 # decode 段 = [0 : num_decode_tokens]
num_prefill_tokens = num_tokens - num_decode_tokens
# 返回四元组 (num_decodes, num_prefills, num_decode_tokens, num_prefill_tokens)

这四个数正落在前言两条恒等式上。有了 num_decode_tokens，后端就能把打平流切成 [:num_decode_tokens]（decode 段）和 [num_decode_tokens:]（prefill 段），各走各的 kernel / wrapper。

为什么即便在 GPU 上也要切：decode 是访存瓶颈（1 query、读整段历史 KV、想最大化 batch）、prefill 是算力瓶颈（多 query、matmul 密集），最优 tiling 不同，塞一个 kernel 会互相拖累。这套"重排 + 切分"是 vLLM 上游通用机制——FlashAttention 用不上它，通用昇腾后端原样复用它。

分水岭：FlashAttention = 一把吃混排（不切）；FlashInfer / MLA / 昇腾 = reorder 成 decode-first、按 num_decode_tokens 切两段各算。

3　PD 分离下的调度与 continuous batching（对照 co-located）

前面 1 / 2 默认按 co-located（混布）讲。本节把散在各处的 PD 小标注集中起来。大前提：调度器是同一套代码、同一套算法——双队列扫描、两个预算、抢占、token 进度差 全不改。PD 分离带来的不是"另一套调度"，而是 ① 每个实例的负载被拆成单一相 ② 多了 KV connector 钩子与一个等待态。

拓扑背景见 Part1·1.2：P = kv_producer 只 prefill、D = kv_consumer 只 decode，各一套完整三进程，中间 KV connector 直连。

3.1　co-located 批内混排与 PD 实例间流水

co-located 里 2 的精髓是 prefill + decode 在同一实例的同一个 batch 里混算——一次 forward 内，计算密集的 prefill 顺带把访存密集的 decode "捎带"算了，两者在同一台设备、同一步里重叠。

PD 分离把两相拆到不同实例，"重叠"换了形态——重叠的是 P 实例对「较新一批请求」的 prefill 计算，与 D 实例对「较早一批请求」的 decode 计算，在同一 wall-clock 时间并行发生（P、D 是两套独立 NPU）。这是一条 2 级生产者–消费者流水线（P = stage1 产 KV、D = stage2 耗 KV）：

异步调度

4　异步调度：相邻 step 重叠、placeholder 与 MTP 回退

前置：Part1「一步数据流」（step() 的调用序）与「execute_model / sample_tokens 两阶段」。Part1 那句"异步调度时与下一步调度重叠"就是本节展开的内容。

其中「多跑一步」是异步调度最容易被忽略的一笔固定开销，而且与 MTP 无关——换来的是每步都省下的 CPU 气泡。

4.3　叠加 MTP：被拒时的回退落在哪

异步调度按"draft token 全部被接受"乐观调度下一步，而 MTP 的草稿可能被拒。要回答的问题是：这个回退具体在哪执行？是不是 schedule(N+1) 之后要额外插一个回退步骤？

结论：没有额外步骤。回退寄生在两处本来就要跑的代码里，而且是两套账各自减一次——Worker 一份、Scheduler 一份，互不依赖。整个"回退"只落在一个标量 num_computed_tokens 上：没有 rollback 状态机、不重调度、不丢弃已派发的 batch。

1　模型入口的执行长度裁决：图 padding 与 DP padding

位置：它夹在「打平成一维 token 流」之后、「建 attention metadata + 真正 forward」之前——是打平流长度最后一次被改的地方，改完就发给设备了。

核心结论：这个方法主要回答两个关联问题——「本步采用哪种图模式、对应哪个静态 shape」和「各 DP rank 最终跑多长」。核心顺序是图初选 → DP 协调 → 按 DP 结果复查图。图初选前虽固定检查入口 SP，但只有 vLLM compilation SP 的 enable_sp 开启时才改变长度。

1.1　三类入口 padding 的作用与层次边界

调度器只决定本步要处理的真实 token。_prepare_inputs 将各请求打平成一维 token 流后得到真实总长 N；这个值对请求语义已经正确，但设备执行还要满足图、跨 DP 通信和可选编译 SP 的 shape 约束。padding 不增加业务 token，而是把动态长度转换成这些机制能够接受的执行 shape。

4　多档位录图、选图与图 padding

主线：CompilationConfig 在配置期确定多个捕获档位，capture_model 在启动期逐档录图，稳态由 CUDAGraphDispatcher.dispatch 选择对应图。精确命中时不需要 padding；没有精确档位时才向上补到最近档位，超过最大档位则退回 eager。多档位图主要服务 Decode；普通 Decode 每请求一步只有 1 token，开启 MTP 后，档位还需要兼容 1 + num_spec。

4.1　两个阶段：启动录图，稳态选图

阶段 A · capture启动期遍历 capture sizes，以对应长度执行 dummy forward，分别保存静态图。
阶段 B · dispatch稳态每步选择 graph mode 与 batch descriptor；精确命中不补槽，只有 S>N 时才 padding。

启动期只为若干固定 shape 建立可复用图；稳态 dispatch 负责选中其中一档。若真实长度 N 已是捕获档位，直接回放对应图；否则才把执行视图扩到最近档位 S。ACLGraphWrapper 不重新判断长度是否合法，而是信任 forward context 中的 graph mode 与 descriptor。

4.2　从档位表到逐档录图

捕获 size 可以显式配置，也可由调度上限生成候选表。普通 Decode 每请求一步为 1 token；开启 MTP 后，uniform decode 的 num_tokens 恒等于 num_reqs × (1 + num_spec)，因此档位需要向上取整到 1 + num_spec 的倍数。档位越密，稳态 padding 浪费越小，但启动录图时间和 graph pool 显存越高。

5.2.1　为什么异步调度改变基类默认选路

为什么异步调度要换路：CPU 准备第 N+1 步时，第 N 步的 forward/sample/MTP 可能仍在设备主流执行。如果下一步 DP 同步的 D2H 也排进同一条流，host 为取得长度和图模式就会连带等待第 N 步完成。两者没有数据依赖，只是被流的 FIFO 顺序串在一起。

同步结果为什么必须读回 host：长度 max、模式 min 虽然在设备上算出，但随后要作为 Python 控制流使用——决定是否 padding、pad 到多少、选择哪张图或回退 eager。因此设备路径最终必须执行 D2H / .item()。

5.3　lm_head 的 DP 对齐

ena_dp_lmhead_parallel 和 ena_local_lmhead_parallel 都会让 lm_head 沿 vocabulary 维做 TP 式权重切分。区别在于切分组：前者把 DP group 的 rank 当作 vocabulary-parallel ranks，后者使用单机 local-world group；若都关闭，则 lm_head 使用模型原有的标准 TP group。

因此代码内部仍使用 tp_rank、tp_size 和 vocabulary-parallel lm_head，但这里的 tp_size 取自所选的 DP/local-world group，不一定等于模型主体的 TP size。按 DP/local-world group 切分后，各 rank 持有不同请求的 hidden，需要 all-gather hidden states，再由各 rank 计算本地 vocabulary shard，最后通过 all-to-all 把完整 logits 换回原请求所在 rank。通信前必须把本地采样 hidden 补到相同长度，通信后再裁回 local_n。

发生时机：每个 DP rank 先走常规调度。只有本地 scheduler 本轮没有产出可执行 batch、但其他 DP rank 仍在运行时，EngineCore 才在执行层调用 execute_dummy_batch。它发生在常规调度之后，不是 scheduler 生成的请求。

为什么不影响调度：dummy batch 不进入 WAITING/RUNNING 队列，不占 scheduler 的 token budget，不改变真实请求的 KV、抢占和完成状态，也不产生用户输出。它只增加一次必要的占位执行，影响执行开销而不改变调度结果。

怎样参与 DP padding：_dummy_run(1) 先建立最小占位输入，再与活跃 rank 一样进入 _determine_batch_execution_and_padding 和 coordinate_batch_across_dp。图模式或 EP 允许 DP padding 时，各 rank 共同确定最大执行长度 S 并重新选图；空闲 rank 也从 1 个 dummy token 扩到 S 个占位槽。因此它在调度语义上是 0 个真实 token，设备执行 shape 却与活跃 rank 一致，可以按相同顺序完成跨 rank 通信；dummy 结果始终丢弃。

小结

6　小结：为什么 padding、在哪里发生、如何隔离

Padding 的核心目的不是增加有意义的 token，而是把动态、不可整除或跨 rank 不一致的数据布局，转换成算子、静态图和集合通信能够接受的 shape。新增位置只是执行槽；真实 token 的边界必须始终保留，并在对应消费者结束后屏蔽或裁回。
